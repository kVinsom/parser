## Чинний комплект Linux/VPS

Готові файли, команди запуску, перенесення з Windows та backup/restore:
[deploy/README.md](../deploy/README.md). Цей комплект використовує Telegram
polling, окремі контейнери bot/worker/parser і постійні томи. Notifier
працює всередині worker. Для ручного checkout є додаткова конфігурація Caddy.
Усі дані чинного бота потрібно відновити до запуску з його токеном.

Нижче збережений початковий план масштабованого розгортання; окремі
worker-scheduler/executor, два Redis і webhook не є поточною реалізацією.

Під час першого розгортання в реєстрі джерел вмикається тільки Vinted. Конфігурації дозволених доменів, проксі, лімітів і адаптерів розділяються за source_id. Наступні сайти підключаються до спільних сервісів після реалізації й перевірки їхніх адаптерів; правила — у [SOURCES.md](SOURCES.md).

Для черг Redis: AOF, постійний том, політика noeviction, підтвердження задач і відновлення pending. Для кешу/FSM — окремий Redis із TTL та власною політикою пам'яті. Втрата кешу не видаляє користувачів, ролі, збережені пошуки, розклад або outbox із PostgreSQL.

PostgreSQL має постійний том, регулярні резервні копії поза основним сервером та перевірку відновлення. Черги/outbox мають обмеження зростання та окремий стан для задач, що вичерпали повторні спроби.

План Docker Compose включає bot, worker-scheduler, worker-executor, parser, access-gateway, **byparr**, notifier, PostgreSQL, Redis для черг, Redis для FSM/кешу та Caddy. Byparr — обраний сторонній сервіс обходу зі своїм браузерним рушієм і налаштованими проксі користувача; власні Python-сервіси не визначають версію його внутрішнього середовища. FlareSolverr залишається вимкненою за замовчуванням альтернативою в окремому профілі. Стек метрик також має окремий профіль. Byparr має налаштовані обмеження ресурсів, а gateway — чергу й паралельність викликів. Вхід з інтернету відкритий лише до webhook через Caddy; API Byparr та інші компоненти працюють у внутрішній мережі. Деталі — у [BYPARR.md](../services/access-gateway/docs/BYPARR.md).

Спосіб підключення готового сервісу валют до розгортання визначається після перегляду його коду/інтерфейсу; його наявний стек не замінюється без потреби адаптації.
