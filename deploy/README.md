# Запуск Vpars на Linux/VPS

Цей комплект запускає чинний бот: bot, worker із notifier, parser, gateway,
Byparr, PostgreSQL та Redis. Windows-планувальник на сервері не потрібний:
контейнери мають `restart: unless-stopped`. Worker звертається до окремого
parser, зберігає регіональні паузи у постійному томі та коректно завершується
за SIGTERM. Міграції виконуються перед запуском bot і worker.

Пошук і меню працюють через Telegram polling: домен і відкриті порти їм не
потрібні. База, Redis, parser, gateway і Byparr не публікують портів хоста.
Для особистого вікна checkout є окрема конфігурація HTTPS нижче.

## Підготовка сервера

Потрібні Linux x86-64, Docker Engine із Compose v2, Python 3.12+ для команд
керування та доступ до Telegram/Vinted або свого проксі. Практичний стартовий
запас — 4 vCPU, 8 GB RAM і 40 GB SSD; це оцінка для браузерів, а не гарантія
місткості. Навантаження залежить від кількості одночасних браузерів і фільтрів.

Для Ubuntu 24.04 порядок встановлення Docker наведений в
[офіційній інструкції](https://docs.docker.com/engine/install/ubuntu/).
Docker має запускатися разом із ОС. Розпакуй **архів вихідного коду** в постійний
каталог, наприклад `/opt/vpars`, і виконуй команди з його кореня. Не перенось
Windows `.venv` та каталоги тестових артефактів як частину вихідного коду.

## Перенесення чинного бота з Windows

Це правильний шлях для поточного проєкту зі збереженими фільтрами й історією.
Не запускай на VPS порожнього бота з чинним токеном перед відновленням бази.
Одночасна робота двох установок із копіями бази може спричинити дублікати:
їхні блокування не спільні між різними PostgreSQL.

1. На Windows під тим самим користувачем, який запускає бот, експортуй
   конфігурацію в приватний файл. Команда переносить чинний токен, режим
   checkout, проксі та ключ шифрування сесій; генерує новий пароль серверної
   бази. Секрети не друкуються й наявний файл не перезаписується.

   ```powershell
   New-Item -ItemType Directory -Force .backups | Out-Null
   services/telegram-bot/.venv/Scripts/python.exe deploy/export_local_secrets.py --output .backups/server.env
   ```

   Ключ Windows DPAPI експортується тільки з початкового облікового запису.
   Не замінюй його новим ключем: інакше збережені зашифровані сесії не
   розшифруються. Якщо ключ відсутній, експортер зупиняється для перевірки.

2. Перед остаточним перенесенням заверши роботу з вікнами покупок. Зупини
   **процеси** локального бота й worker та їх автоматичне відновлення.
   Це не команда персонального Stop у Telegram: наміри пошуків зберігаються.

   ```powershell
   & deploy/stop_local.ps1
   services/telegram-bot/.venv/Scripts/python.exe deploy/export_local_data.py --env-file .backups/server.env --output .backups/server-transfer
   ```

   Експортер перевіряє відсутність робочих блокувань, бере їх на час копіювання,
   зберігає PostgreSQL, історію, фільтри, права, покоління запусків, профілі,
   контракти браузера й регіональні паузи. Redis/FSM і браузерний кеш не
   переносяться: незавершений діалог меню можна відкрити заново.
   Підтримано поточний локальний PostgreSQL із `services/telegram-bot/compose.yaml`;
   для іншої бази експортер відмовиться працювати замість вибору навмання.
   Зупинка процесу під час мережевого надсилання може залишити штатний
   `DeliveryUncertain`; такі записи не слід вручну повертати до масової розсилки.

3. Передай каталог `server-transfer` на VPS через SSH/SFTP окремо від архіву
   коду. Він містить приватні дані й секрети. Обмеж доступ до нього. На VPS:

   ```bash
   cd /opt/vpars
   install -m 600 /secure/server-transfer/private.env deploy/.env
   python3 deploy/manage.py check
   python3 deploy/manage.py build
   python3 deploy/manage.py restore /secure/server-transfer
   python3 deploy/manage.py start
   python3 deploy/manage.py status
   ```

   Відновлення перевіряє SHA-256 і допускає лише порожню базу та порожні томи
   стану. Наявні дані автоматично не очищаються. Якщо відновлення перервалося,
   не запускай бот до з'ясування стану; повтор поверх частково відновленої
   бази навмисно буде відхилений. Команда `restore` не запускає bot і worker.

4. Перевір `/start`, наявні фільтри й статус пошуків, а також журнал worker.
   Успішний healthcheck підтверджує процес і залежності; новий збіг та
   відповідь Telegram перевіряються окремо. Обмеження Vinted і проксі
   залежать від мережі VPS. Windows-установку залиш вимкненою.

Браузерні профілі Windows можуть містити прив'язані до ОС cookies або
посилання на Chrome/Edge, яких немає на Linux. Архів зберігає ці дані,
але сумісність входу не гарантується: може знадобитися повторне підключення
Vinted через меню бота. У серверному образі є Chromium; купівлю після
перенесення потрібно окремо перевірити з власним акаунтом. Шифровані записи
PostgreSQL зберігаються з початковим ключем.

Для відкату спочатку зупини сервер (`python3 deploy/manage.py stop`), перенеси
назад актуальні дані, якщо на сервері вже були зміни, і тільки потім запускай
Windows. Старий знімок бази не міститиме нових доставок із VPS. Локальні
процеси запускаються через `start.ps1`; відновлення задачі Windows —
`Enable-ScheduledTask -TaskName 'vpars-worker-recovery'`.

## Чиста установка без перенесення даних

Використовуй лише для справді нового бота/порожньої установки:

```bash
python3 deploy/configure.py
nano deploy/.env
python3 deploy/manage.py check
python3 deploy/manage.py start
```

`configure.py` генерує приватний файл із новим паролем і ключем шифрування.
Потрібно вписати `TELEGRAM_BOT_TOKEN`, за потреби проксі. Для пароля PostgreSQL
використовуй згенероване hex-значення, щоб не потребувати екранування URL.
Зміна пароля в `.env` не змінює пароль уже створеної бази PostgreSQL.

## Щоденна робота, оновлення й копії

```bash
python3 deploy/manage.py status
python3 deploy/manage.py logs
python3 deploy/manage.py backup
```

Копія створюється в `.backups/<UTC-час>/` із контрольними сумами. На час
копіювання bot і worker зупиняються; потім запускаються тільки ті, які
працювали до копіювання. Копія включає приватну конфігурацію: зберігай її
з обмеженим доступом і копіюй на окреме захищене сховище. Автоматичний
розклад і зовнішнє сховище в цьому комплекті не налаштовані.

Для оновлення: зроби копію, заміни вихідний код, збережи `deploy/.env` і томи,
виконай `python3 deploy/manage.py stop`, потім `python3 deploy/manage.py start`.
Образ перебудується, міграції виконаються перед процесами. Не використовуй
`docker compose down -v`: це видалить томи даних. Звичайний `stop` зберігає
дані та особисті Start/Stop; для відновлення процесів виконай `start`.

Для перенесення серверної копії на новий хост: установи її `private.env`
як `deploy/.env`, збери образи, виконай `restore <каталог>` на порожній
установці, а потім `start`. Не запускай одночасно старий і новий хост.

Логи Docker обмежені трьома файлами по 10 MB на контейнер. Docker перезапускає
процес після аварійного виходу; статус `unhealthy` сам собою не викликає
перезапуску. Тимчасові помилки PostgreSQL/Redis обробляє supervisor.
Перевірка bot/worker дивиться на робоче блокування в PostgreSQL і Redis;
parser/gateway/Byparr перевіряються власними endpoint. Це не зовнішній моніторинг.

## Покупка кнопкою в чаті

Поточний режим: `WALLET_CHECKOUT_MODE=bot`. Buy надсилає повну суму та кнопку
Approve. Лише після Approve бот перевіряє суму повторно, оплачує з балансу
й надсилає результат у чат; за нестачі коштів покупка зупиняється. Не потрібні
домен, Cloudflare, Mini App або `--handoff`. Збережена авторизація Vinted,
готові дані доставки та перевірене оформлення потрібні до ввімкнення оплат.
`WALLET_CACHE_CAPACITY=4` та `WALLET_CACHE_IDLE_SECONDS=300` керують кешем
фонових браузерів; сесії інших акаунтів залишаються на диску.

Деталі й межі живої перевірки: [Buy у боті](../docs/BOT_BUY_2026-10-12.md).

## Попередній режим: покупка після Buy через HTTPS

Потрібен домен із DNS на VPS та доступні порти 80/443.
У `deploy/.env` задай `WALLET_HANDOFF_URL=https://checkout.example.com`
зі своїм доменом та `WALLET_CHECKOUT_MODE=balance_first`. Потім:

```bash
python3 deploy/manage.py --handoff check
python3 deploy/manage.py --handoff start
```

Надалі для цієї установки додавай `--handoff` і до інших команд керування.
Caddy працює в мережевому просторі bot і звертається до його loopback-порту
8086; зовні доступний HTTPS, порт браузера не публікується. Вибір цього
режиму без URL залишає пошук і меню доступними, але вікно покупки потребує
налаштування HTTPS. Без домену й облікового запису цей шлях наживо не перевірений.

Цей самий домен передається worker: Buy у нових картках одразу відкриває
оформлення через Telegram Mini App. Окрема реєстрація не потрібна — власника
визначає підпис Telegram. Підключена сесія Vinted повинна бути доступною на VPS.
Локальна адреса Chrome `127.0.0.1:9223` із Windows на VPS не працюватиме;
після перенесення потрібне підключення браузера на самому сервері.

Після перевірки HTTPS і підключення Vinted онови Buy у вже надісланих картках.
Команда без `--apply` лише підраховує доступні картки:

```bash
docker compose --env-file deploy/.env -f deploy/compose.yaml -f deploy/compose.handoff.yaml exec -T -w /app/services/telegram-bot bot python -m vpars_bot.wallet_upgrade_buttons
docker compose --env-file deploy/.env -f deploy/compose.yaml -f deploy/compose.handoff.yaml exec -T -w /app/services/telegram-bot bot python -m vpars_bot.wallet_upgrade_buttons --apply
```

При зміні домену оновлення кнопок потрібно повторити. Caddy забезпечує HTTPS
без тестового тунелю Cloudflare.

`balance_first`: після Buy бот перевіряє повну суму й оплачує тільки з
балансу Vinted у межах збереженого ліміту. Для цього потрібні активний
гаманець, готові дані доставки та перевірений контракт checkout цього акаунта.
За нестачі коштів відкривається те саме оформлення для ручного вибору оплати.
Автоматичної доплати з картки немає. Невизначений результат списання блокує
повтор. `manual` залишає оплату повністю користувачеві; він доступний як
окремий режим. Порожній або неперевірений контракт не дозволяє автооплату.

Перед перенесенням перевір [поточний стан живої перевірки](../docs/DIRECT_BUY_2026-10-12.md).
Проходження синтетичних тестів не означає, що Vinted-акаунт уже готовий
до реальної автооплати або що публічний endpoint розгорнуто.

## Перевірено під час підготовки 11.10.2026

- Збірка Linux-образів у Docker Desktop; запуск окремого тестового Compose.
- Міграції з порожньої PostgreSQL, готовність worker/parser/gateway/Byparr/Redis.
- Chromium із sandbox від непривілейованого користувача.
- Запуск bot, polling через локальний імітатор Telegram та звільнення
  блокування після SIGTERM. Справжніх тестових повідомлень і покупок не було.
- Повний backup → restore в іншій PostgreSQL зі збереженням двох користувачів,
  Nike/Adidas, виключень, доступів, Start/Stop, поколінь, історії та темпу регіону.
- Автоматичний перезапуск worker після SIGKILL: контейнер знову healthy,
  `restart_count=1`; збережені дані повторно перевірені.
- **61** тест worker: налаштування, спільні пошуки, ізоляція та відновлення.
  Додаткові перевірки пакування, архівів і налаштування секретів.
- Синтаксис Compose із додатковим HTTPS та `caddy validate` успішні;
  справжній домен і отримання сертифіката ще не перевірялися.

Доступу до цільового VPS ще немає. Фінальне перенесення реальних даних,
серверний проксі, реальна доставка Telegram, перезавантаження самого VPS
та HTTPS checkout перевіряються під час запуску там. Чинні локальні пошуки
й особисті налаштування під час підготовки не змінювалися.

Офіційні довідки, за якими налаштовано запуск:
[Compose readiness](https://docs.docker.com/compose/how-tos/startup-order/),
[Playwright Docker](https://playwright.dev/python/docs/docker#crawling-and-scraping).
