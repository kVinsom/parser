# Архітектура access-gateway

[README сервісу](../README.md) · [Спільні патерни](../../../docs/PATTERNS.md) · [Доступ](ACCESS.md) · [Byparr](BYPARR.md)

Статус: проєктування майбутнього коду. Gateway приховує від parser конкретні клієнти, проксі та способи доступу до сайту.

## Патерни

| Патерн | Робота в цьому сервісі |
|---|---|
| Ports & Adapters + Facade | Сценарій FetchResource приймає дозволений запит і повертає відповідь або типізовану помилку через один інтерфейс |
| Strategy + Adapter | HTTP через curl_cffi і ByparrClient реалізують спільний порт доступу; стратегія вибирає маршрут за політикою джерела |
| Registry | source_id визначає дозволені домени, регіони, адаптер і можливості; спочатку зареєстрований Vinted |
| Bulkhead | Окремі бюджети одночасних викликів для джерел, маршрутів/проксі та браузерного сервісу |
| Circuit Breaker + Retry | Повторюються лише тимчасові помилки в межах бюджету; несправний маршрут тимчасово призупиняється, потім перевіряється обмеженим пробним викликом |
| Rate Limiter + Backpressure | Частота й паралельність контролюються окремо; обмежена черга не дає перевантажити Byparr |
| Single Flight | Одночасне оновлення одного ключа сесії виконує один власник; інші очікують його результат або повертають кероване відкладення |

## Межі модулів

- `application/fetch_resource` — перевірка запиту, бюджет часу, вибір стратегії, підготовка результату.
- `application/ports` — AccessClient, SessionStore, RateLimiter, Clock.
- `adapters/outbound/sources/vinted` — політика доступу Vinted і регіонів.
- `adapters/outbound/http_client` та `byparr_client` — конкретні клієнти; додатковий браузерний провайдер підключається окремим адаптером.
- `adapters/outbound/session_store` — ізольовані метадані/cookies та координація оновлення. Результат записується тільки чинним власником операції.
- `adapters/inbound/http` — валідація DTO і виклик сценарію без логіки доступу в HTTP-обробнику.

## Шлях запиту

Перевірити source_id/регіон/ресурс → зарезервувати ресурси → отримати придатну сесію → виконати HTTP або Byparr → перевірити відповідь → повернути дані. За тимчасової помилки допускається обмежений повтор із затримкою та випадковим розкидом; відповідь блокування класифікується окремо.

Ключ сесії включає джерело, регіон, проксі й профіль клієнта. Перенесення cookies між маршрутами допускається тільки за перевіреної сумісності. Single Flight стосується операції оновлення; він не означає, що Byparr має постійний спільний браузер. Життєвим циклом свого браузера керує сам Byparr.

Типові результати помилок: RateLimited із retry_after, AccessBlocked, ProxyUnavailable, UpstreamTimeout, InvalidResource, CapacityUnavailable. HTTP 200 зі сторінкою перевірки не є успішним каталогом. Чутливі дані проксі не передаються у повідомленні помилки.

## Швидкодія та перевірка

HTTP-з'єднання повторно використовуються; browser-операції мають окремий обмежений ресурсний бюджет. Для кількох реплік загальний ліміт провайдера/проксі координується через Redis, бо окремий ліміт у кожному процесі множив би загальне навантаження. Коротка локальна черга обмежується строком запиту; довгострокове повторення належить worker.

60 викликів Byparr за хвилину — ціль кількості надісланих запитів. Ліміт одночасних запитів підбирається за тривалістю й ресурсами; це окрема величина. Правила джерела та retry_after можуть тимчасово зменшувати частоту.

Під час реалізації перевірити ізоляцію сесій, ліміт між репліками, одночасне оновлення сесії, таймаут і скасування запиту, відмову одного маршруту та блокування замість каталогу. Реальну сумісність Byparr із Vinted перевіряє інтеграційний прототип.

Опис механізмів: [Bulkhead](https://learn.microsoft.com/en-us/azure/architecture/patterns/bulkhead), [Circuit Breaker](https://learn.microsoft.com/en-us/azure/architecture/patterns/circuit-breaker).
