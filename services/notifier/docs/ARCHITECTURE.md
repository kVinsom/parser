# Архітектура notifier

[README сервісу](../README.md) · [Спільні патерни](../../../docs/PATTERNS.md) · [Доставка](DELIVERY.md) · [Валюти](../../currency-adapter/docs/INTEGRATION.md)

Статус: проєктування майбутнього коду. Сервіс перетворює довговічний намір доставки на повідомлення Telegram і записує результат.

## Патерни

| Патерн | Робота в цьому сервісі |
|---|---|
| Outbox Relay + Consumer | Relay публікує ID готових записів PostgreSQL у Redis; виконавці беруть їх у роботу, а стан у БД дозволяє відновлення |
| Idempotent Consumer | Повтор одного outbox_id не надсилає лот повторно, якщо запис уже успішний, скасований або обробляється чинним власником |
| Delivery State Machine | Кожна спроба має явний стан, власника й час наступної дії, включно з невідомим результатом Telegram |
| Distributed Rate Limiter + Priority | Загальний бюджет бота й обмеження чату спільні для всіх реплік та відповідей telegram-bot; меню отримує пріоритет |
| Message Builder | Форматування лота відокремлене від отримання курсу, перевірки доступу й мережевої відправки |
| Adapter + Fallback | TelegramSender приховує aiogram; за явної недоступності фото готується текст, за помилки конвертації — вихідна ціна |
| Repository + Unit of Work | Резервування, результат спроби, message_id і облік успішної доставки зберігаються узгоджено |

Outbox не робить зовнішню відправку атомарною з PostgreSQL. Relay може повторно публікувати запис; унікальність і перевірка стану потрібні на стороні отримувача. [Transactional Outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html).

## Межі модулів

- `application/relay_outbox` — публікація готових ID й відновлення незавершених записів.
- `application/deliver_notification` — резервування, конвертація, очікування ліміту, повторна перевірка доступу й відправка.
- `domain/message_builder` — чисте формування тексту лота, фото та кнопки джерела; шаблони нагадувань додаються на етапі 2.
- `domain/delivery_state` — дозволені переходи й політика невідомого результату.
- `application/ports` — TelegramSender, CurrencyClient, DeliveryRepository, RateLimiter, Clock.
- `adapters/outbound` — aiogram, PostgreSQL, Redis, валютний HTTP-клієнт за фактичним інтерфейсом.

Relay може бути циклом у процесі notifier. Окремий мікросервіс для нього не потрібен. Redis передає сигнал виконати роботу, а PostgreSQL визначає актуальний стан. Втрата сигналу усувається повторною перевіркою готових outbox-записів.

## Стани та одноразовий ефект

Основний шлях: `pending → leased → sending → sent`. Допоміжні стани: `retry_wait`, `unknown`, `cancelled`, `failed`. Резервування має строк і токен власника; перехід стану виконується умовним оновленням, щоб дубль задачі не захопив ту саму спробу.

- До початку зовнішньої відправки можна безпечно повернути задачу з простроченої оренди на повтор.
- Якщо відправка вже почалася, а результат не записаний, відновлення переводить її в unknown; можливе успішне повідомлення в Telegram.
- Для unknown діє погоджена політика: одна відкладена повторна спроба з ризиком дубля, потім failed для розбору. Цей лічильник зберігається в PostgreSQL.
- sent зберігає message_id; повторний outbox_id не відправляється. Успіх одночасно фіксує доставку користувач + канонічний лот. Скасований намір не дорівнює успіху.

За явної тимчасової помилки зберігаються причина та next_attempt_at. retry_after задає мінімальний час повтору. За помилки фото текстовий fallback застосовується лише коли відомо, що первинне повідомлення не надіслане; таймаут із невідомим результатом проходить шлях unknown.

## Доступ і швидкодія

Перед відправкою перевіряються can_monitor, активність, покоління, версія фільтрів і delivery_epoch. На етапі 1 звичайний пошук не залежить від підписки, кількості предметів чи адмінролі. Для доставки достатньо одного чинного активного збігу. Глобальний delivery_epoch змінюється при повному Stop, source_delivery_epoch — при повній зупинці джерела.

Перевірка виконується після конвертації й очікування ліміту. Відправка, Stop і зміна пошуку серіалізуються щодо рішення почати надсилання. Зовнішній запит, що вже почався, може завершитися після Stop.

На етапі 2 додаються окремий тип нагадування, ключ дедуплікації за користувачем/джерелом/версією підписки та перевірки строку/ролі. Квоти перевірятимуться спільною політикою без зміни логіки Telegram-відправки. До завершення всього бота ці модулі не потрібні. План — у [ROADMAP.md](../../../docs/ROADMAP.md).

Черга має обмежену кількість одночасних відправок; гарячий чат не займає всі слоти. Короткі резервування й перевірки в БД відокремлені від мережевого очікування. Дані лота читаються порціями, доступні file_id фото повторно використовуються, конвертація має обмежений бюджет часу. Якщо курсу немає, доставка вихідної ціни продовжується.

Під час реалізації перевірити дубль outbox, збій до/після Telegram-виклику, unknown і одну повторну спробу, Stop під час очікування ліміту, відсутність тарифного блокування, 429, недоступність фото/валют і блокування бота. Загальні ліміти надсилання враховуються згідно з [Telegram FAQ](https://core.telegram.org/bots/faq#my-bot-is-hitting-limits-how-do-i-avoid-this).
