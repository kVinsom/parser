# Планування та виконання пошуків

Чинні правила 08.10.2026: доступ LITE/PRO/ULTRA, підтверджений вік до 60 секунд
для всіх користувачів. Нижче згадана історична політика 25.09 не діє.
Невизначений обхід після 20 сторінок або 100 запитів сповільнюється на 30–300 с
між продовженнями; курсор зберігається, початок видачі перевіряється окремо.
Повтор тієї самої повної сторінки не просуває курсор і не завершує покриття.

Поточна реалізація 2026-10-01: збережений прохід до контрольної межі, перекриття
сторінок і повторна перевірка початку видачі. `Pages` обмежує порцію роботи;
незавершене продовження зберігається в `catalog_jobs.scan_state`. Подробиці та
актуальні правила: [README](../README.md), [звіт](../../../docs/CATCHUP_AUDIT_2026-10-01.md).

Історична реалізація 2026-09-25: перша сторінка за новизною, мовчазний початковий
прохід, довговічна історія всіх побачених ID для кожного покоління пошуку,
доставка тільки ID, вперше побачених після початкового проходу цього запуску.
Ліміт 60 секунд і обов'язкова дата публікації скасовані за підтвердженням
користувача. Відома дата до Start або в майбутньому все ще відсікається.
Новизна ID не доводить час публікації продавцем.
Неповний перелік ID не завершує ініціалізацію; картки з неповними атрибутами
все одно запам'ятовуються за ID. Рестарт процесу не
скидає історію; новий Start робить новий початковий прохід.
Подробиці: [журнал](../../../docs/WORK_LOG.md). Опис Taskiq і повного обходу
сторінок нижче залишається проєктом масштабованої архітектури.

[README сервісу](../README.md) · [Підписки](../../telegram-bot/docs/SUBSCRIPTIONS.md) · [Доставка](../../notifier/docs/DELIVERY.md)

Стек: asyncio, Taskiq, Redis Streams, SQLAlchemy Async/PostgreSQL.

Два процеси одного сервісу: планувальник і масштабовані виконавці завдань.

- Планувальник читає next_run_at активних запитів, резервує прострочені задачі короткою орендою та публікує їх у чергу. Після збою оренда спливає і задача відновлюється.
- Для однакового нормалізованого запиту до одного source_id/region_id з однаковим значущим контекстом каталогу виконується одне завантаження, а результати перевіряються для всіх зацікавлених користувачів. Запити різних сайтів не об'єднуються; запити різних регіонів одного сайту не об'єднуються без перевірки еквівалентності каталогів.
- Не запускає одночасно дві перевірки того самого запиту; обмежує конкуренцію за сайтом, регіоном і ресурсами gateway. Помилка або пауза одного сайту не зупиняє задачі інших.
- Викликає parser, зіставляє лоти з фільтрами й перевіряє can_monitor: власник, неархівований предмет, вибране ввімкнене джерело та придатні фільтри. Для виконання також потрібні активність і актуальне покоління частини. Тариф, строк підписки та ліміти перевіряються спільною політикою entitlements.
- Після Stop, архівування або редагування інвалідовує зачеплені частини й повідомлення без жодного чинного активного збігу. Якщо лот також підходить іншому активному предмету, він залишається придатним. Спільні запити продовжуються, доки мають активних учасників.


- Зберігає лоти й завдання надсилання в одній транзакції PostgreSQL через outbox.
- Відстежує вже надіслані лоти окремо для кожного користувача. Знання лота в загальній базі не означає, що його вже отримали всі користувачі.
- Обходить сторінки до попередньої межі перегляду з невеликим перекриттям. Якщо досягнуто ліміту пагінації чи відповіді неповні, фіксує прогалину та планує дозавантаження, не стверджує повноту збору.
- Повторні запуски задач повинні бути ідемпотентними; дані для відновлення розкладу зберігаються в PostgreSQL.

Кожна задача каталогу містить source_id та region_id. Повний Stop скасовує всі персональні задачі й невідправлені лоти; ручний Start створює нове покоління й не оживляє старі наміри. Доступ перевіряється за чинним тарифом перед виконанням і доставкою; прострочення призупиняє недозволені запуски.
