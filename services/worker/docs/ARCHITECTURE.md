# Архітектура worker

[README сервісу](../README.md) · [Спільні патерни](../../../docs/PATTERNS.md) · [Моніторинг](MONITORING.md) · [Етап 2: підписки](../../telegram-bot/docs/SUBSCRIPTIONS.md)

Статус: проєктування майбутнього коду. Планувальник та виконавці — процеси одного сервісу з різними точками запуску.

## Патерни

| Патерн | Робота в цьому сервісі |
|---|---|
| Producer–Consumer / Competing Consumers | Планувальник створює роботу, кілька виконавців розбирають її з черги з обмеженою паралельністю |
| Durable Scheduler | next_run_at і запуски зберігаються в PostgreSQL; перезапуск процесу не втрачає розклад |
| Lease + Fencing Token | Задача резервується на обмежений час; запис результату дозволений лише чинному поколінню виконавця |
| Request Coalescing + Fan-out | Одна перевірка однакового каталогу дає лоти кільком зацікавленим користувачам |
| Specification | Спільна функція зіставляє лот із фільтрами: AND між параметрами, OR між альтернативами |
| Repository + Unit of Work | Контрольні точки, лоти й наміри доставки змінюються узгодженими транзакціями |
| Transactional Outbox + Idempotent Consumer | Робота та повідомлення відновлюються після збоїв, повторна задача не повторює вже зафіксований ефект |

## Межі модулів

- `application/schedule_due_queries` — вибір запитів, яким настав час, і створення записів запуску.
- `application/check_catalog` — отримання сторінки parser, перевірка поточного запуску й передача результатів на зіставлення.
- `application/match_and_enqueue` — перевірка фільтрів/доступу, відсікання повторів і створення notification_outbox.
- `application/stop_searches` — повний Stop та інвалідація частин після архівування/редагування. ExpireAccess, ReconcileSearchQuota і планування нагадувань не входять до етапу 1.
- `domain/matching` — чисті перевірки полів; `application/ports` — ParserClient, репозиторії, Publisher, Clock.
- `adapters/inbound/tasks`, `adapters/outbound/postgres` і `redis` — брокер та збереження; `scheduler_main` і `executor_main` — складання двох типів процесів.

## Життєвий цикл перевірки

1. Планувальник короткою транзакцією резервує готові записи та створює унікальний запуск. Рекомендовано `FOR UPDATE SKIP LOCKED`, щоб кілька планувальників не очікували один на одного на тій самій порції задач. Це механізм для вибору роботи з черги, а не для перевірки прав. [PostgreSQL SELECT](https://www.postgresql.org/docs/current/sql-select.html).
2. Публікація в Redis відбувається після commit. Непідтверджена публікація відновлюється з довговічного запису query_jobs; повторна публікація має той самий ID запуску.
3. Виконавець атомарно отримує оренду з токеном покоління, перевіряє потребу в запиті та викликає parser без відкритої довгої транзакції БД.
4. Перед записом результату перевіряються токен оренди й актуальний стан. Прострочений виконавець не змінює контрольну точку та не створює повідомлень. Після аварії можливий повтор мережевого завантаження, але його результат проходить ту саму перевірку.
5. Придатні лоти, стан перегляду та outbox записуються транзакційно. Черга підтверджується після збереження завершення або довговічного плану повтору. Повторний виклик завершеного запуску повертає вже відомий результат.

Одночасний запит об'єднується тільки за повним ключем: source_id, region_id, нормалізовані фільтри та значущий контекст каталогу. Потреба одного користувача не зникає через Stop іншого; перед доставкою кожен користувач перевіряється окремо.

## Фільтри, повтори та скасування

Specification повертає збіг, незбіг або непідтверджений результат. Відсутність атрибута, потрібного активному фільтру, не є збігом. Функції мапінгу сайту належать parser; worker перевіряє спільну модель без залежності від Vinted.

При створенні outbox перевіряються can_monitor, версія фільтрів, активність/покоління частини, глобальний delivery_epoch і source_delivery_epoch. Can_monitor не читає підписки або тарифні місця. Повний Stop скасовує всю персональну роботу; архівування чи редагування — лише зачеплені частини. Новий Start не робить старі результати придатними. Коротка транзакція узгоджує outbox зі змінами пошуку.

Outbox зберігає відповідні search_id/source_id з поколіннями й версіями фільтрів. Для доставки достатньо одного чинного активного збігу; втрата іншого збігу не скасовує повідомлення. source_delivery_epoch змінюється при повній зупинці джерела.

Унікальність доставленого лота задається користувачем і канонічним лотом з урахуванням джерела. Окремо відсіюються одночасні невідправлені наміри. Скасований намір не прирівнюється до успішної доставки; створення наступного повідомлення підпорядковується чинним правилам повторного пошуку.

Тимчасова помилка переносить next_attempt_at з обмеженим числом повторів. Непридатний формат, вичерпаний бюджет або остаточна помилка переходять у збережений failed із причиною для розбору. Gateway керує короткими мережевими повторами; worker не запускає паралельно каскад повторів кожної внутрішньої ланки.

Зміна адмінролі на етапі 1 не впливає на звичайний моніторинг. На етапі 2 спільна політика отримає перевірки підписок і кількості предметів; worker — задачі завершення доступу, квот і нагадувань. Вони описані в [ROADMAP.md](../../../docs/ROADMAP.md) і не потрібні для першого запуску.

## Швидкодія та перевірка

Однакові пошуки об'єднуються, робота вибирається індексами за строком/станом, лоти записуються порціями. Великі транзакції на всіх користувачів розбиваються на відновлювані порції з перевіркою доступу для кожної; контрольна точка просувається тільки після довговічного збереження необхідних результатів.

Під час реалізації перевірити збій до/після публікації в Redis, дубль задачі, втрату оренди, конкурентний Stop/Start, стару версію фільтрів, часткову пагінацію, зміну адмінправ і дедуплікацію між пошуками. Підтвердження та pending-відновлення перевіряються разом із [taskiq-redis](https://github.com/taskiq-python/taskiq-redis).
