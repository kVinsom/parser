# Контракти Telegram-сервісу

Цей документ описує реалізований код станом на 2026-09-22. Старі документи
архітектури залишаються описом цільових міжсервісних зв’язків.

## Предмети та фільтри

`Search.id` — UUID, власник — незмінний 64-бітний Telegram ID.
Картки зберігаються в `bot_searches`, версії фільтрів — `bot_search_versions`.
FSM містить лише чернетку, поточний крок, ID операції й дані панелі. Строк життя
чернетки — 24 години. Втрата Redis не видаляє картки або ролі. Старий callback
без відповідного поточного екрана не виконується.

`Filters` містить списки `models`, `sizes`, `conditions`, `colors`, `brands`,
`keywords`, `categories`; `sources` — словник `source_id → region_id[]`;
`price` — необов’язкові межі та обов’язкова для заданої ціни валюта EUR/GBP.
Decimal серіалізується в JSON рядками; float не використовується.

Поточний reply-діалог створює `follow_enabled_sources=true`: один бренд,
одна модель, кілька розмірів, ціна та ключові слова в кінці. Колір, категорія
та стан у цьому сценарії порожні. `sources` зберігає початковий набір;
при кожному Start беруться всі актуально ввімкнені маркетплейси користувача.
Для нового майданчика створюється власний `SearchRun`, якщо його ще немає.

`native_prices` — словник `GBP/EUR → {minimum, maximum} | null`.
Бот сам визначає валюти за ввімкненими країнами та запитує дві межі для кожної.
`null` означає свідомий пропуск ціни. Перед командою worker `for_source`
залишає тільки відповідний маркетплейс і матеріалізує звичайний `price`
у його валюті; `native_prices` очищується, `follow_enabled_sources=false`.
Отже, GBP та EUR мають незалежні межі, а кожна команда містить конкретні
параметри для одного джерела. Результат конвертації не використовується.
Якщо згодом увімкнено нову валюту, для якої ще немає меж, ціни іншої валюти
не копіюються: запуск просить налаштувати новий фільтр. Повністю необмежена
ціна поширюється й на нові країни. Старі збережені фільтри з `price`
та фіксованими `sources` залишаються сумісними.

Між полями діє AND, між альтернативами — OR. Модель/ключова фраза означає
наявність усіх слів однієї альтернативи в назві без урахування регістру;
опис лота не перевіряється цим сервісом. Порожній список прибирає обмеження.
Відсутній атрибут не підтверджує активний фільтр. Сам matcher належить майбутньому worker/parser.

До 8 альтернатив по 100 ASCII-символів на текстовий параметр — технічний
захист розміру діалогу, не тариф або обмеження кількості карток. Довгі значення
в підсумку скорочуються з `…`, у базі зберігаються повністю. Числа, коди й
розділові знаки дозволені; кирилиця у значеннях фільтрів відхиляється.

## Джерела та можливості

`SourceRegistry` читає `config/sources.json`. Кожна країна Vinted є окремим
маркетплейсом: `vinted_gb`, `vinted_fr`, `vinted_it`, `vinted_de`. Кожен запис має
`provider="vinted"` та один регіон. Адаптер worker вибирає реалізацію parser
за `provider`, а країну — за регіоном цього маркетплейсу. GB приймає UK як
аліас; чинний parser приймає обидва коди. PL не можна ввімкнути конфігурацією.
Інші маркетплейси додаються записом джерела та власним адаптером, а кнопки
вибору регіонів утворюються з реєстру. Сам запис у конфігурації не реалізує сайт.

`CapabilityProvider.describe(source_id, regions)` повертає `CapabilityReport`:
для кожного параметра `supported`, `unsupported` або `unknown`, необов’язковий
перевірений довідник і ознаку актуальної перевірки. `issues(filters)` повертає
причини неможливості запуску. Довідники у стандартному адаптері відсутні.
За замовчуванням можливості не вважаються перевіреними. Колір і категорія
Vinted позначені як непідтримувані на підставі наявного
`services/parser/vpars_parser/sources/vinted.py`; їх можна зберегти в чернетці,
але Start заблоковано з поясненням. Для інших значень потрібна перевірка
конкретного parser при майбутньому підключенні. Живий API можливостей зараз не викликається.

Регіони Vinted GB мають GBP, FR/IT/DE — EUR. Активний фільтр ціни з іншою
валютою видимо блокує Start. Для кількох валют користувач пропускає ціну або
створює окремі картки. Майбутній UAH-конвертер стосується показу ціни,
ніколи не перераховує фільтри.

## SearchControlPort та майбутній worker

Порт має асинхронні `start(user_id, operation_id, search_id=None)`,
`stop(user_id, operation_id)` і `status(user_id)`.
`PersistentSearchControl` змінює стан і додає команду в `bot_control_commands`
однією транзакцією PostgreSQL. Бот не читає цю таблицю для виконання моніторингу.
Це контракт команд, а не друга черга надсилання Telegram.

Одна частина картки на маркетплейсі — рядок `bot_search_sources` із поколінням.
GB, FR, IT та DE мають окремі рядки, стани та покоління. Стан `requested` означає збережений запит,
`active` — підтвердження реального worker з чинною орендою,
`stopped` — зупинку, `demo` — симуляцію без права доставки.
`SEARCH_ADAPTER=unavailable` є стандартним режимом; він не підтверджує запуск.

Команда `start` містить `filters`, `simulation` та `token`:

```json
{
  "user_id": "Telegram ID у JSON є числом",
  "search_id": "UUID",
  "source_id": "vinted_fr",
  "delivery_epoch": 0,
  "generation": 1,
  "filter_version": 1
}
```

Це пояснення структури, а не готове завдання зі справжнім ID.
Майбутній worker має:

1. Прочитати команду, перевірити поточні стан, власника, фільтри, джерела й token;
   ідемпотентно прийняти її за `ControlCommand.id`. Механізм читання/ack команд
   і транспорт worker реалізуються окремо. `simulation=true` ніколи не запускає реальний пошук.
2. Перевірити підтримку всіх активних фільтрів через parser і можливість моніторингу.
   `unknown` не є дозволом на реальний запуск. Не надсилати неперевірені збіги.
3. Лише після фактичного запуску викликати інтеграційний метод
   `acknowledge(WorkToken, lease_seconds=60)`; поновлювати оренду, поки моніторинг
   працює. Максимум оренди — 300 секунд. Це внутрішній Python-метод, публічного
   HTTP endpoint для довільних підтверджень немає.
4. Не вважати прострочене підтвердження активним: меню повертається до
   «запуск не підтверджено». Покоління не змінюється при повторному Start
   вже прийнятої частини; дубль моніторингу не створюється.

`stop` одразу підвищує глобальний `bot_users.delivery_epoch`, зупиняє всі
частини й підвищує їхні покоління в одній транзакції. Всі давні персональні
завдання та повідомлення стають непридатними, включно з retries та пізніми
результатами. Повторний Start не оживляє старі tokens. Запізніле завершення
Start після Stop відхиляється перевіркою epoch. Картки та історія залишаються.

Редагування/архівування підвищує версію картки, інвалідовує її частини та
додає `invalidate`; інші картки й інші користувачі не зачіпаються.
Відновлена картка зупинена до ручного Start.

`bot_users.enabled_sources` зберігає вибір маркетплейсів: `NULL` зберігає
попередню поведінку (усі налаштовані джерела), `[]` вимикає всі. Start передає
лише перетин джерел картки з цим вибором; зміна вибору під час перевірки
можливостей скасовує застарілий запуск. Вимкнення майданчика підвищує
покоління тільки його частин і додає `invalidate` з відповідним піднабором
`generations`. Інші джерела продовжують працювати. Повторне ввімкнення
не запускає пошук автоматично і не відновлює старі токени.
`acknowledge` та `can_deliver` також перевіряють персональний вибір джерела.

Міграція `0004` розгортає старі `sources={"vinted": ["FR", "DE"]}` у
`{"vinted_fr": ["FR"], "vinted_de": ["DE"]}` у картках та історії. ID, версії,
архівний стан і решта фільтрів зберігаються. Старий вибір `vinted` вмикає всі
чотири країни, порожній вибір залишається порожнім. Старі частини Vinted
замінюються зупиненими частинами країн; старі команди не переписуються й
не можуть підтвердити запуск через змінені ID. Інші джерела продовжують працювати.
Читання старих чернеток підтримує спільний ключ `vinted` і нормалізує його.
Downgrade до `0003` згортає країни назад: будь-яка вибрана країна означає
ввімкнений спільний Vinted, оскільки старий інтерфейс не має окремих перемикачів.

Майбутній notifier повинен безпосередньо перед відправленням перевірити
`can_deliver(token)` або еквівалентні умови актуальної бази. Достатньо хоча б
одного чинного підтвердженого збігу. Історія доставок і дедуплікація лотів
належатимуть notifier/worker; у боті вони не підміняються фіктивними записами.
Вже розпочатий зовнішній Telegram-запит неможливо гарантовано відкликати.

## Ціни й шаблони

`CurrencyConverter.to_uah(Decimal, currency)` асинхронно повертає `Conversion`
або `None`. Результат містить суму, валюту та необов’язкові `rate_at`,
`fetched_at`, `provider`. `UnavailableCurrencyConverter` завжди повертає `None`.
`optional_conversion` обмежує час очікування, приймає тільки коректний UAH
і повертає `None` при помилці/таймауті, зберігаючи оригінальну ціну.

Чистий `format_lot(lot, conversion=None, demo=False)` повертає `LotMessage`:
`text`, `keyboard`, `photo_url`. Відправник використовує `sendPhoto` з підписом,
коли `photo_url` присутній, і `sendMessage` без фото. При відмові завантаження
фото майбутній notifier може використати ту саму текстову картку.
Форматувальник сам не надсилає запити й не споживає чергу.

`lot_messages.prepare_lot` поєднує необов’язкову конвертацію з чистим
форматувальником. `send_lot_message` реалізує вибір фото/тексту та перехід до
тексту при відхиленому фото. Він не вибирає отримувача, не читає чергу й не
авторизує доставку: викликати його можна лише після перевірки актуального
покоління. `/example` використовує його тільки для явно позначеного прикладу
в режимі розробки; у production команда недоступна.

Всі атрибути екрануються для HTML, довжина обмежена для підпису 1024 UTF-16
одиниць. Невідомі атрибути пропускаються, HTTP(S)-посилання береться тільки
з лота. Некоректні URL не стають кнопками. Без конвертера показується лише
оригінальна ціна; з результатом — `≈ сума грн`. `demo=True` додає помітну
позначку «Приклад — демонстраційні дані».

## Транзакції, адмінправа та відновлення

Операції пошуків блокують рядок власника. Ефект і запис `bot_operations`
фіксуються разом. Стабільний ID чернетки захищає від повторного створення,
версія картки — від перезапису застарілим редактором.

Адміноперації серіалізуються рядком `bot_guards/admins`, після чого блокують
виконавця й отримувача в порядку ID. Це захищає від одночасного зняття
останнього адміністратора й відкликання прав між перевіркою та commit.
`RoleEvent.operation_id` унікальний; роль та аудит атомарні. Звичайні пошуки
не перевіряють роль, оплату або кількість карток. Початкове призначення
записує `bootstrapped=true`, що не скидається при перезапуску.

Профіль надходить лише з власного Telegram User у приватному чаті.
Нормалізований username унікальний, зміна/видалення ніка не переносить роль.
Старі update_id не перезаписують новіший профіль; після понад 7 днів тиші
дозволяється новий відлік ID Telegram. Перед вибором і підтвердженням отримувача
виконується `getChat` за його збереженим ID, а не пошук приватної особи за ніком.
Помилка або невідповідність закриває адміноперацію без зміни прав.

`bot_inbox` має ключ `(bot_id, update_id)`. Приймач записує подію перед
підтвердженням. Один процес обробляє до `INBOX_CONCURRENCY=8` різних чатів через
aiogram. `lane_key` і запит `FOR UPDATE SKIP LOCKED` зберігають порядок подій
одного чату; його пауза не блокує інші чати. Redis додатково ізолює FSM.
Оренда `lease_token/lease_until` триває `HANDLER_TIMEOUT + 10` секунд;
після аварії подія доступна після закінчення оренди. Застарілий обробник
не може записати результат поверх нового власника оренди. Після успіху payload
очищується, ключ ідемпотентності залишається. Мутації захищені власними операціями.

Stop від власника приватного чату виконується в тій самій транзакції, що й
приймання події, через `stop_in_transaction`. ID `inbox-stop:<update_id>`
використовується також під час подальшої обробки меню, тому повтор не підвищує
epoch удруге. Відсутній користувач не створюється. Для Start/Run зберігається
`search_epoch` на момент приймання: запит, прийнятий до Stop, не відновлює пошук
після нього. У polling пакет розбивається навколо Stop, щоб наступний Start
отримав новий epoch. Нова натиснута кнопка Stop працює також зі старого меню.

У `MENU_MODE=menu` приймач розпізнає текстові кнопки «✅ Почати пошук» та
«❌ Завершити пошук» (також старі назви з ▶️/⏹), а також команду `/stop`.
У головному меню показується лише одна кнопка за збереженим станом пошуку.
Старі inline-callback ігноруються
і при прийманні, і в обробнику. У `full` діють попередні inline-Start/Run/Stop
та `/stop`. У `preview` жодна кнопка чи `/stop` не змінюють пошук.
Режим передається однаково до класифікації події та її подальшої обробки,
щоб зупинка при прийманні й відповідь меню використовували одну операцію.

Перед відправленням меню Redis зберігає `pending_panel` та ID події. Повтор
цієї події після невдалої відправки надсилає вже підготовлений екран, не виконує
перехід діалогу ще раз. Однаковий екран не викликає зайве редагування Telegram.
Це не гарантія exactly-once доставки: при втраті відповіді на `sendMessage`
або втраті Redis повтор повідомлення все ще можливий.

Після 8 звичайних невдач inbox залишає `failed`, назву класу помилки й payload
для діагностики. `TelegramDeferred` і `TelegramRetryAfter` переносять
`next_attempt_at`, не витрачаючи спроб; Telegram `retry_after` не скорочується
до локальної максимальної паузи. Спільний Redis-бюджет обмежує повідомлення
всього бота та окремого чату; отриманий `429` тимчасово затримує весь бюджет
повідомлень. Підтвердження кнопок і приймання команд мають окремий шлях.
Журнали не містять токена, URL API, тексту повідомлення або
SQL-параметрів. Для діагностики можна прочитати тільки
`bot_id, update_id, state, attempts, last_error`. Після усунення причини
оператор може адресно перевести перевірений запис у `received`, обнулити
`attempts`, встановити `next_attempt_at=now()`. Застаріла чернетка або кнопка
потребуватиме повторного відкриття меню; привілеї не відновлюються з payload.
Повторне призначення активної оренди вручну потребує зупинки відповідного
обробника; для відновлення завершеного `failed` оренда вже очищена.

Майбутній notifier має використовувати той самий `RedisTelegramBudget`,
`bot_id` та Redis-базу, інакше його запити не враховуються в бюджеті меню.
Notifier/споживач доставки тут не реалізований; пріоритет меню над його лотами
потрібно забезпечити при підключенні. Деталі — [LATENCY.md](LATENCY.md).

Міграції створюють тільки таблиці з префіксом `bot_`; таблиць оплат,
моніторингу каталогів або доставки лотів немає. У розгортанні кожен бот
повинен мати власну базу/схему; advisory lock працює між приймачами одного
бота, що використовують ту саму базу.
