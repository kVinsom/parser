# Архітектура telegram-bot

[README сервісу](../README.md) · [Спільні патерни](../../../docs/PATTERNS.md) · [Діалоги](DIALOGS.md) · [Етап 2: підписки](SUBSCRIPTIONS.md) · [Адмінправа](ADMINS.md)

Статус 2026-09-22: Telegram-сервіс реалізовано в пакеті `vpars_bot`.
Нижче збережено цільові патерни й логічні межі; фактичні модулі, inbox та
інтеграційні контракти описані в [INTEGRATION.md](INTEGRATION.md).
Бот веде діалоги й зберігає сценарії керування. Worker, notifier і конвертер
валют ще не підключені; Start без worker не показується як активний моніторинг.

## Патерни

| Патерн | Робота в цьому сервісі |
|---|---|
| Finite State Machine | Кроки введення фільтрів, username і підтвердження мають явні стани та дозволені переходи |
| Thin Handler + Use Case | aiogram-обробник розбирає подію й викликає окремий сценарій, який містить бізнес-правила |
| Repository + Unit of Work | Пошук/роль, журнал операції та ідемпотентність змінюються однією транзакцією |
| RBAC + Shared Access Policy | Роль перевіряє адміндії; спільна entitlements перевіряє тариф, строк, ліміти, власника, джерело та стан |
| Inbox + Idempotency Key | Повторний update або підтвердження не створює дубль пошуку й не змінює роль вдруге |
| Per-user Serialization | Одночасні повідомлення одного користувача обробляються узгоджено, щоб не перескочити крок діалогу |
| Dependency Injection | Сценарії отримують сховища, Clock і клієнт перевірки профілю; тести не потребують живого Telegram |

FSM реалізується через aiogram та RedisStorage; ролі й підтверджені фільтри належать PostgreSQL. [aiogram FSM](https://docs.aiogram.dev/en/latest/dispatcher/finite_state_machine/index.html).

## Межі модулів

- `adapters/inbound/telegram/routers` — меню, фільтри, пошуки й адміндії.
- `adapters/inbound/telegram/dialogs` — стани, тексти, клавіатури й перехід до наступного запиту.
- `application` — SaveFilters, AddSearchItem, ArchiveSearchItem, RestoreSearchItem, StartSearch, StopAllSearches, GrantAdmin, RemoveAdmin, ResolveUsername. Підписки та ReconcileSearchQuota додаються на етапі 2.
- `domain` — правила фільтрів/доступу та значення; спільні правила імпортуються з узгодженого доменного пакета.
- `adapters/outbound` — репозиторії PostgreSQL, Redis FSM, TelegramProfileClient, спільний ліміт надсилання.
- `bootstrap` — webhook, маршрути, залежності й життєвий цикл клієнтів.

## Діалоги та конкурентні події

Для окремої картки використовуються стани model → size → наступні параметри → review. «Додати ще» доповнює поточний параметр, «Пропустити» прибирає його обмеження. «Зберегти» перевіряє власника/версію, підтверджує чернетку й підвищує версію фільтрів у транзакції. Паралельні дії не дублюють картки; тарифні місця не перевіряються.

Для адмінправ: recipient_username → review → confirmed. Операція фіксує внутрішній ID отримувача; підтвердження повторно перевіряє профіль і права виконавця. Інший акаунт не підставляється автоматично. Деталі — у [BOT.md](BOT.md#пошук-користувача-за-username).

Кожен діалог має версію/ідентифікатор; callback від попереднього екрана не виконує нову зміну, крім власної команди Stop, яка зупиняє пошук уже при прийманні. Для одного користувача використовується узгоджена обробка подій із короткою орендою/блокуванням і перевіркою версії. Сам RedisStorage не вважається гарантією одноразового виконання операції: остаточний захист — транзакція та унікальний ID операції в PostgreSQL.

## Надійність webhook і доступу

Webhook спочатку зберігає вхідну подію в inbox із ключем `(bot_id, update_id)`, після чого повертає підтвердження Telegram. Обробник переводить запис received → processing → processed; зависла обробка відновлюється. Для змін у PostgreSQL ефект та завершення операції записуються атомарно. Повтор відповіді меню після мережевого збою можливий, повтор зміни ролі або створення картки — ні.

Чернетка FSM має строк життя, а погоджені фільтри — постійне зберігання. Втрата Redis може перервати незавершений діалог; бот повідомляє про потребу пройти його знову, не відновлює привілейовану дію з довільного старого callback. Inbox не позначається успішно обробленим до завершення відповідного сценарію.

Повний Stop підвищує глобальний delivery_epoch; архівування й редагування інвалідовують зачеплені частини пошуку. Can_monitor не звертається до підписок: звичайні пошуки однаково доступні всім користувачам. Мережеві виклики виконуються поза довгою транзакцією; перед commit перевіряються версії та чинна роль виконавця для адміндій. Платні правила підключаються пізніше через спільну перевірку за [ROADMAP.md](../../../docs/ROADMAP.md).

## Швидкодія та перевірка

Різні чати обробляються паралельно; порядок подій одного чату зберігається. Підтвердження натискань не очікує бюджету відправлення меню, а Stop фіксується в PostgreSQL при прийманні. Бот не чекає parser/Byparr для відповіді на Start: він зберігає запит для майбутнього worker. Фактичний пошук і notifier ще не підключені; їхній спільний бюджет та пріоритет меню потрібно зберегти при інтеграції. Реалізовані обмежувачі, виміри та межі гарантій описані в [LATENCY.md](LATENCY.md).

Під час реалізації перевірити покрокове введення, подвійні натискання, одночасні відповіді, повтор update, втрату FSM, зміну username, зняття прав під час підтвердження та повний Stop. Додавання й запуск понад 10 предметів не повинні блокуватися тарифом на етапі 1; після зняття адмінправ звичайний пошук продовжується.
