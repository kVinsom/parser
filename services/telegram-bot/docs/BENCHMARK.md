# Повна затримка команди — 2026-09-23

Виконано 240 локальних вимірів повного шляху команди та 5 дозволених живих
запитів до Telegram у підтверджений приватний чат. Також пройшли 71 автономний
і 18 інтеграційних тестів. Середовище: Windows, Python 3.12.14, локальні
PostgreSQL/Redis у Docker; стандартні налаштування бота.

## Що означає «загальна затримка»

Відлік починається перед локальним HTTP POST із командою до webhook і закінчується,
коли HTTP-клієнт бота отримує успішну відповідь Bot API. Усередині заміру:

`HTTP → перевірка/розбір події → запис inbox у PostgreSQL → черга → aiogram →
Redis FSM → бізнес-логіка/меню → Redis-бюджет → HTTP Bot API → відповідь API`.

Окремо виміряно завершення запису `processed` після відповіді API. Всі записи
в перевірених сценаріях завершилися успішно. Бюджет повідомлень, повтори та
пауза `retry_after` працювали як у застосунку.

Це **повний серверний шлях**, а не час від дотику до екрана до появи відповіді
на телефоні. Не виміряно доставку команди від пристрою через Telegram,
зовнішній reverse proxy та відображення на пристрої. Telegram-час повідомлення
не дає достатньої точності для такого заміру в мілісекундах.

## Живий Telegram

Користувач дозволив 5 тестових відповідей і надіслав `/start`. Перевірено
єдиного приватного відправника; використано справжній токен із локального `.env`.
Проведено 5 послідовних команд із паузою 1,1 с між завершеннями, без навмисної
черги. Було створено одну позначену тестову панель і виконано 4 її оновлення.
Кнопки прибрано, реальний пошук не запускався.

| Вимір | Кількість | Медіана | Максимум |
|---|---:|---:|---:|
| Весь шлях до відповіді Telegram API | 5 | **92,84 мс** | **190,64 мс** |
| Весь шлях до завершення запису inbox | 5 | 103,07 мс | 202,01 мс |
| HTTP-виклик надсилання/редагування | 5 | 57,18 мс | 130,63 мс |
| Весь шлях після першої команди | 4 | 90,95 мс | 95,60 мс |
| Окремий `getMe` з повторним використанням з’єднання | 10 | 31,32 мс | 36,86 мс |

П’ять загальних затримок: **190,64; 95,60; 89,06; 92,84; 88,41 мс**.
Усі команди виконано за одну спробу, по одному запиту повідомлення на команду.
Перший запит панелі відкривав нову HTTP-сесію; наступні використовували її повторно.

Середня тривалість до `processed` — 121,30 мс. Приблизний розподіл середнього:
6,93 мс приймання, 27,58 мс обробника без API, 71,14 мс API, 15,64 мс черги,
планування й службових операцій inbox. Очікування до першого обробника входить
в останню складову; повторно додавати його не потрібно. Різниця округлень — 0,01 мс.

**Окремий початковий запит перевірки токена `getMe` зайняв 4231,92 мс.**
Це було до п’яти команд, тому він не включений у їхню медіану. На момент
живого бенчмарку середовище вже виконувало запити Telegram. Причина першого
викиду не вимірювалась окремо за DNS/TCP/TLS; приписувати його саме серверам
Telegram немає підстав. Отже, близько 0,1 с — спостереження цього сеансу,
не гарантія для першого підключення чи іншого маршруту мережі.

У вибірці з п’яти команд p95 і p99 збігаються з максимумом; статистики
недостатньо для надійної оцінки рідкісних виробничих затримок.

Сирі результати: [живий тест](../.artifacts/benchmark-live.json),
[початкова перевірка API](../.artifacts/telegram-connection.json).

## Локальний бенчмарк під навантаженням

Реальні HTTP-клієнт/сервер, PostgreSQL, Redis, aiogram, обробник `/start`,
збережена картка, FSM та обмежувач. Тільки зовнішній Telegram замінено
локальним HTTP-сервером із заданою затримкою або відповіддю `429`.
Ліміт — 25 запитів/с на бота, мінімум 1 с на чат, 8 паралельних обробників.
Кожний сценарій повторено тричі з новою схемою/ключами.

| Сценарій | Команд | p50 | p95 | Максимум |
|---|---:|---:|---:|---:|
| Поодиноке меню, задана пауза API 50 мс | 60 | 99,03 мс | 101,06 мс | 128,45 мс |
| Поодиноке меню, задана пауза API 250 мс | 60 | 299,65 мс | 315,27 мс | 407,63 мс |
| Одночасно 32 різні чати, API 50 мс | 96 | 1172,31 мс | 2292,86 мс | 2865,81 мс |
| Одночасно 5 команд одного чату, API 50 мс | 15 | 2313,59 мс | 4484,00 мс | 4484,00 мс |
| `429` із вимогою почекати 3 с | 3 | 3275,66 мс | 3376,15 мс | 3376,15 мс |

Ще 6 команд охоплюють Stop під час відповіді API із паузою 2 с.
Ефект Stop записано за **16,08–17,31 мс**, медіана **16,40 мс**;
видиме підтвердження Stop надійшло через **2108,19–2126,04 мс**.
Отже, затримана відповідь не затримує саме зупинення пошуку.

Пауза API задається через асинхронний таймер; його точність і планувальник
Windows впливають на фактичний час. У JSON записані саме виміряні значення,
не підставлена константа 50/250 мс. Одночасні webhook-запити можуть бути прийняті
в іншому порядку, ніж їхній запуск клієнтом; підсумки не припускають цього порядку.

Статистика обчислена по всіх окремих командах трьох повторів. p95/p99 —
nearest rank, p50 — медіана; початкові запити кожного повтору включено.
Підготовка схеми та створення тестових користувачів/карток виконуються до відліку.

Сирі результати й хеші коду: [240 вимірів](../.artifacts/benchmark-total.json).
Ці числа не можна безпосередньо порівнювати з попереднім тестом лише inbox
із [LATENCY.md](LATENCY.md): тепер додано весь діалог, Redis, HTTP та бюджет.

## Повторення

З каталогу `services/telegram-bot`:

```powershell
./run.ps1 --test -m 'not integration' --durations=10
./run.ps1 --integration -m integration --durations=10
.venv\Scripts\python.exe tools/benchmark_total.py --output .artifacts/benchmark-total-new.json --runs 3
```

Окремий сценарій: додати, наприклад, `--scenario burst_32_chats`.
Локальний інструмент не завантажує токен і не надсилає повідомлень Telegram.

Живий інструмент запускай тільки після дозволу власника тестового чату
і його `/start`, за відсутності іншого приймача/webhook:

```powershell
.venv\Scripts\python.exe tools/benchmark_live.py --send-test-responses --count 5 --output .artifacts/benchmark-live-new.json
```

Він реально надсилає/редагує тестову панель, обмежений максимумом 5 запитів
і зупиняє подальші відправлення після невизначеного мережевого результату.
Токен читається лише з локальної конфігурації. Якщо відправників `/start`
немає або їх кілька, нічого не надсилає. Отримані Telegram updates читаються
без просування offset і залишаються для звичайного запуску бота.
