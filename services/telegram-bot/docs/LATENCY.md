# Затримки Telegram-бота

Оновлено 2026-09-23. Зміни стосуються тільки Telegram-сервісу.
Worker, parser, notifier і конвертер валют не підключалися.

Подальший замір усього серверного шляху, 5 справжніх запитів Telegram
і навантаження з HTTP/Redis/обмежувачем наведено в [BENCHMARK.md](BENCHMARK.md).
Числа нижче стосуються попереднього вузького тесту внутрішньої черги.

## Що змінено

- До 8 чатів обробляються одночасно. Події одного чату виконуються за порядком
  приймання; повільний запит або повтор іншого користувача їх не блокує.
  Приймання нових подій пробуджує обробник без колишнього очікування 200 мс.
- Polling записує пакет оновлень однією транзакцією. Кожний Stop розділяє
  пакет, щоб правильно впорядкувати його відносно Start.
- Stop зареєстрованого користувача зберігається разом із вхідною подією,
  до очікування меню чи Telegram API. Старий прийнятий Start не скасує Stop.
  Це діє після отримання події ботом: доставку самої команди від Telegram
  або недоступність PostgreSQL таким способом прискорити неможливо.
- У polling підтвердження кнопки виконується окремо: до 4 одночасних запитів,
  до 64 очікувань, загальний таймаут 1 с. Помилка підтвердження не скасовує дію.
  У webhook `answerCallbackQuery` повертається у відповіді після збереження
  події, без окремого запиту. Це прибирає індикатор очікування, а результат
  дії показується окремим меню. Telegram не повертає результат такого виклику
  у відповіді webhook. [Документація Telegram](https://core.telegram.org/bots/faq#how-can-i-make-requests-in-response-to-updates).
- Однакове меню не редагується повторно. Підготовлений екран зберігається
  перед відправленням; повтор після збою Telegram не перемикає крок діалогу
  повторно, якщо цей стан Redis збережений.
- Оновлення незміненого профілю не займає спільне блокування всіх профілів.
  Головне меню рахує картки через SQL COUNT та читає незалежні дані паралельно.
- На перевіреному Windows-хості підключення через `localhost` створювало
  додаткове очікування. Локальні стандартні адреси замінено на `127.0.0.1`.

## Обмеження Telegram

Telegram радить уникати понад одного повідомлення за секунду в одному чаті;
для безкоштовної масової розсилки орієнтир — приблизно 30 повідомлень/с.
Це не гарантована пропускна здатність. [Офіційний FAQ](https://core.telegram.org/bots/faq#my-bot-is-hitting-limits-how-do-i-avoid-this).

Стандартний бюджет бота — 25 запитів повідомлень/с і мінімум 1 с між
повідомленнями або редагуваннями одного чату. Застосування тієї ж паузи до
редагувань — консервативне налаштування сервісу. Дуже швидка послідовність
натискань тому може чекати, навіть коли інтернет працює добре.

Резервування бюджету атомарне в Redis, використовує його час і спільні ключі
`telegram-budget:{bot_id}:…`. Якщо Telegram повертає `429`, бот враховує
повний `retry_after` плюс малий запас, зберігає спільну паузу для повідомлень
і переносить подію в PostgreSQL. Пізніша коротша пауза не скорочує довшу.
Ці відкладення не витрачають 8 спроб обробки звичайних помилок.
[Значення retry_after](https://core.telegram.org/bots/api#responseparameters).

Додаткові процеси надсилання мають використовувати той самий бюджет.
Зараз окремого notifier немає. Власні серверні затримки Telegram, мережевий
маршрут і обов’язкову паузу `429` бот усунути не може. Webhook не скасовує
лімітів і не обов’язково швидший за вже відкритий long polling.

## Параметри

| Змінна | Стандартно | Призначення |
|---|---:|---|
| `INBOX_CONCURRENCY` | 8 | Кількість одночасно оброблюваних чатів, від 1 до 32 |
| `HANDLER_TIMEOUT` | 20 с | Межа однієї спроби обробки; потім відкладений повтор |
| `TELEGRAM_REQUEST_TIMEOUT` | 7 с | Таймаут звичайного запиту Telegram |
| `TELEGRAM_CONNECTION_LIMIT` | 40 | Пул HTTP-з’єднань; щонайменше concurrency + 6 |
| `TELEGRAM_MESSAGES_PER_SECOND` | 25 | Глобальний бюджет повідомлень, не понад 30 |
| `TELEGRAM_CHAT_INTERVAL` | 1 с | Мінімальна пауза повідомлень одного чату |
| `WEBHOOK_MAX_CONNECTIONS` | 40 | Паралельні вхідні з’єднання webhook, від 1 до 100 |

Для long polling залишено 25 с очікування нових подій і 35 с мережевого
таймауту; це не затримка вже отриманої події. Сесія HTTP використовується
повторно. Оренда події та Redis-блокування діалогу тривають ще 10 с після
межі обробника. Після аварійного завершення відновлення чекає закінчення оренди.

Перед запуском оновленої версії: зупинити попередній процес, виконати
`./run.ps1 --migrate`, запустити `./run.ps1 --serve`. Міграція `0002` додає
поля та індекси черги, заповнює їх для наявних подій; картки і ролі зберігаються.
Для Docker вкажи адреси сервісів PostgreSQL/Redis, не `127.0.0.1` хоста.

## Як спостерігати затримки

Кожні 60 с журнал `vpars_bot` містить `Latency statistics`. У webhook-режимі
той самий знімок доступний через `/health` після перевірки PostgreSQL/Redis.
Тексти повідомлень, ID користувачів і токен у ці метрики не потрапляють.

- `inbox.ingest` — запис вхідного пакета, включно зі Stop за його наявності.
- `inbox.queue` — вік події до початку кожної спроби; повтори включають паузу.
- `inbox.handler` — тривалість спроби, включно з очікуванням Telegram.
- `telegram.<method>` — тривалість викликів API; long polling сюди не входить.
- `telegram_429`, `outbound_deferred`, `inbox.deferred`, `inbox.errors`,
  `callback_ack_failed` — лічильники відповідних обмежень і збоїв.

Для кожного виду тривалості зберігаються останні 512 вимірів: p50, p95, максимум
і кількість. Це діагностика конкретного процесу, що скидається при перезапуску,
а не прогноз мережі або вимір часу від натискання в застосунку користувача.
Зростання `telegram.*` вказує на затримку виклику; зростання `inbox.queue` при
звичайному часі API — на накопичення подій чи очікування бюджету. Через
`next_attempt_at` можна побачити час наступної спроби після отриманого `429`.

## Вимірювання на цьому комп’ютері

32 оновлення різних чатів, справжній локальний PostgreSQL, імітатор із затримкою
50 мс на кожне оновлення. Показано медіану трьох запусків до та після змін.
Початковий запуск використовував `localhost`, новий — `127.0.0.1`, тому
порівняння відображає сукупність змін черги та підключення. Запуски зроблені
в різний час; це локальний орієнтир, а не контрольований мережевий тест.

| Вимір | До | Після |
|---|---:|---:|
| Запис пакета 32 подій | 90,63 мс | 7,74 мс |
| p50 від запуску обробника черги до завершення імітатора | 1040,22 мс | 270,85 мс |
| p95 того самого часу | 1872,07 мс | 397,58 мс |
| Завершення останнього імітатора | 1995,92 мс | 413,82 мс |

p95 зменшився приблизно на 79%. Імітатор не викликає Telegram API, не проходить
через вихідний бюджет і не вимірює повний aiogram-діалог. Тому ці цифри
характеризують внутрішню чергу, а не реальну швидкість доставки повідомлень.
Звіти: `.artifacts/latency-before.json`, `.artifacts/latency-after.json`.

Окремий вимір двох нових з’єднань: Redis — 4151,42 → 4,86 мс,
PostgreSQL — 2093,43 → 48,39 мс при заміні `localhost` на `127.0.0.1`.
Це властивість перевіреного середовища; не всі комп’ютери мають таку затримку.
Звіт: `.artifacts/loopback-latency.json`.

Повторити тест черги без токена й повідомлень людям:

```powershell
.venv\Scripts\python.exe tools/benchmark_latency.py --output .artifacts/latency-current.json --runs 3
```

Інструмент створює випадкову тимчасову схему `bench_bot_*` і видаляє тільки її.
Для іншої тестової бази використовуй `TEST_POSTGRES_URL`.
