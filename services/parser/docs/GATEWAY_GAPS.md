# Залежності від подальшого розвитку gateway

Це пропозиції окремих сумісних задач, **не вже додані поля protobuf**.
Поточний parser використовує чинну схему без змін.

## Порожній каталог і завершення пагінації

Gateway класифікує PAGE_LOADED за наявністю товарних посилань; порожня сторінка
стає UNEXPECTED_CONTENT, її HTML не передається. Parser не може відрізнити
відсутність товарів від помилки формату чи доступу. Зараз повертається явна
помилка `UnexpectedContent` з джерельним статусом.

Мінімальна окрема зміна: на реальних зразках підтвердити ознаки порожнього
каталогу та відрізнити їх від CAPTCHA, редиректів і незавантаженої сторінки.
Додати сумісний позитивний результат підтвердженого порожнього каталогу або
окреме явне свідчення порожнечі; передавати перевірений HTML/метадані для нього.
Не перейменовувати будь-який UNEXPECTED_CONTENT на успіх. Після цього додати
реальні fixtures і відповідну підтримку в parser.

Кінець сторінок також потребує реальної останньої сторінки/пагінаційних метаданих.
Самої відсутності кнопки недостатньо. До підтвердження — `has_more="unknown"`.

## Товарні фільтри й сортування

FetchCatalog має лише регіон, текст і сторінку. Потрібно окремо перевірити
джерельні способи фільтрації, актуальні довідники та семантику AND/OR; потім
додати типізовані параметри й перелік підтримуваних можливостей gateway.
Довільний URL/закритий endpoint або вигадані ID довідників не є заміною контракту.

Для ціни потрібна валюта, для розміру — контекст категорії/системи розмірів.
Для newest-first потрібна підтверджена семантика сортування. Кілька текстових
моделей не можна склеювати у вужчий текстовий запит. Якщо потрібні кілька запитів
для OR, fan-out і окремі сторінки має явно планувати worker.

## Відсутні атрибути

Підтверджені картки дають бренд, стан, розмір; не дають кольору, категорії й
однозначної доступності. Для них потрібні реальні дані у доступному форматі.
Якщо знадобиться окреме завантаження деталей, його бюджет і контракт узгоджуються
окремо; parser не відкриває приховано кожне оголошення.

Мапінги вікових/категорійних розмірів і неоднозначних станів потребують
підтверджених довідників. Додавати підписки, тарифні квоти чи персональну
дедуплікацію до цих змін не потрібно.
